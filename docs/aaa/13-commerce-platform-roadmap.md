# 13. 쇼핑몰 종합 솔루션 로드맵 — 설계

- 지시: Ren 2026-11-27 「궁극적으로 스마트스토어센터처럼 쇼핑몰 종합 솔루션을 만들고 싶다. 토모·요루·에어쉽은 같은 페이지에서 관리하고 싶다. 쇼핑몰·구매대행·배대지 고객사를 모집해 사이트를 만들어 주고, 내 운영 노하우와 AI 로 CS·주문 처리를 혼자서도 쉽게 하게 해 주는 솔루션.」 이후 「ㄱ」.
- 상태: 설계만. 코드·DB 변경 없음.
- 판단 기준: 운영 사고·돈 누락·고객 혼란이 가장 적은 쪽. 작업량은 근거로 쓰지 않는다.
- 확인한 사실(2026-11-27 코드): 에어쉽 `migrate-vercel` 최신은 `ced9b1a3` 이고 TOMO 브리지 코드(A1)는 아직 없다. tomo 메인 폴더에 `app/api/ops` 가 아직 없다(T3 미병합). 에어쉽 `admin_menu_access` 는 화면을 가리는 장치이고 「행 없음 = 전체 접근」이다. 에어쉽 `integration_secrets` 는 `provider` 를 키로 쓰는 표이고 서버만 읽는다. 에어쉽 「보는 사이트」는 `src/lib/admin-site.ts` 가 localStorage 로만 들고 있다.
- 확인 못 한 것: 키라팝 운영 표·RPC 구조(2단계 첫 작업에서 읽는다), 에어쉽 하드코딩 상수의 전체 자리(3단계 첫 작업에서 목록을 뽑는다), 시장 가격의 현재 값(8장 숫자는 부모가 준 조사 값 그대로다).

## 1. 제품 그림

**추천 구조 한 줄: 사이트마다 DB·배포를 따로 두고, 공통 「운영 API 규격」으로 통합 관리 화면(센터)에 연결한다. 에어쉽·요루만 지금처럼 같은 DB 에 둔다(혼합형).**

제품은 「여러 쇼핑몰·구매대행·배대지 사이트를 한 화면에서 운영하고, AI 직원이 CS 와 주문 처리를 먼저 해 두는 운영 센터」다. 운영자는 센터에 한 번 로그인한다. 위쪽 「보는 사이트」에서 사이트를 고른다. 홈에는 모든 사이트의 「내 차례」가 합쳐져 보인다. 사이트를 고르면 그 사이트가 가진 기능만 메뉴로 뜬다. 고객은 각 사이트의 이름·도메인·알림만 본다. 센터의 존재는 고객에게 보이지 않는다.

### 1.1 3층 구조

| 층 | 무엇 | 정본이 어디 있나 | 지금 있는 것 |
|---|---|---|---|
| ① 센터(통합 관리 화면) | 사이트 전환, 합친 「내 차례」, 시스템 상태, 알림, 결정 대기함, 권한, (나중) 요금 | 센터 DB: 연결 목록·권한·이벤트·조작 기록·AI 원장만. 주문·돈은 두지 않는다 | 에어쉽 어드민(39화면), 홈 「내 차례」, MorningBrief |
| ② 사이트(테넌트) | 스토어 화면, 주문·회원·돈의 정본 DB, 결제 계정, 알림 발신, 워커 | 사이트마다 자기 DB | 에어쉽+요루(같은 DB), tomo(별도), 키라팝(별도, 다른 법인) |
| ③ AI 운영 직원 | CS 초안·자동 답변, 상태 변화 안내, 아침 보고, 승인 묶음, 원장 | 규칙·원장은 센터. 실행은 운영 API 를 거쳐 사이트에서 일어난다 | 에어쉽 코드의 AI CS 초안·분류·출력 가드·결정 대기함. Aside 스킬·루틴(제품 코드 아님) |

- 원칙 1: 주문과 돈의 정본은 항상 사이트 DB 하나다. 센터는 복사본을 정본처럼 쓰지 않는다.
- 원칙 2: 센터가 죽어도 사이트는 판다. 사이트 하나가 죽어도 다른 사이트와 센터는 돈다.
- 원칙 3: 사이트끼리 돈·통계를 합쳐 보여 주지 않는다. 통화·수수료·소유 법인이 다르다.

### 1.2 「스토어 전환」 사용 흐름

| 단계 | 운영자가 하는 일 | 화면이 하는 일 |
|---|---|---|
| 1 | 센터에 로그인한다 | 내가 권한을 가진 사이트 목록만 읽는다 |
| 2 | 홈을 본다 | 사이트별 「내 차례」 건수를 합쳐 보여 준다. 응답 없는 사이트는 0 이 아니라 「확인 못 함」으로 표시한다 |
| 3 | 「보는 사이트」에서 TOMO 를 고른다 | TOMO 가 선언한 기능(capabilities)만 메뉴로 그린다. 화면 위쪽에 사이트 이름 띠를 항상 보여 준다 |
| 4 | 주문 상태를 바꾼다 | 운영 API 로 요청한다. 사이트가 자기 규칙으로 실행한다. 결과를 다시 읽어 보여 준다 |
| 5 | 돈 조작(환불·출금)을 누른다 | 그 사이트의 돈 권한을 서버에서 확인한다. 사이트 이름·금액·대상을 요약하고 한 번 더 확인받는다 |
| 6 | 다른 사이트로 바꾼다 | 열려 있던 조작 창을 닫는다. 이전 사이트의 대상이 새 사이트 화면에 남지 않게 한다 |

- 사고 방지: 문의 답변·환불 화면에는 사이트 이름과 색을 항상 띄운다. 사이트를 헷갈린 답변과 환불이 가장 큰 혼란 원인이다.

## 2. 테넌트 구조

### 2.1 대안 비교

| 기준 | (가) 한 DB 공유(tenant_id + RLS) | (나) 사이트마다 DB·배포 분리 + 운영 API | (다) 혼합: 에어쉽·요루는 지금대로, 나머지는 분리 **(추천)** |
|---|---|---|---|
| 다른 고객사 데이터가 보이는 사고 | 정책 한 줄 누락으로 생긴다. 에어쉽은 RLS·권한·결제·알림·워커가 전역이라 고칠 자리가 많다 | 구조상 생기지 않는다 | 외부 고객사는 구조상 생기지 않는다. 에어쉽·요루 사이만 남고, 둘 다 Ren 사이트다 |
| 돈이 섞이는 사고 | Stripe 키 1세트라 고객사 매출이 Ren 계정으로 들어온다. 정산·환불 책임이 Ren 에게 온다 | 고객사 결제 계정·계좌를 그 배포에만 넣는다. 섞일 길이 없다 | 같다 |
| 장애 번짐 | 한 고객사의 무거운 조회·잘못된 마이그레이션이 전부를 멈춘다 | 그 사이트만 멈춘다 | 같다. 에어쉽·요루는 같이 멈춘다(지금과 같다) |
| 고객 혼란(이름·발신) | 알림 발신·사업자 표기가 전역이라 다른 이름으로 나갈 수 있다 | 배포마다 자기 설정만 읽는다 | 같다 |
| 내보내기·해지 | 행을 골라 뽑고 골라 지워야 한다. 누락 위험이 있다 | DB 를 통째로 내보내고 통째로 지운다 | 같다 |
| 코드가 갈라지는 사고 | 없다 | 포크를 허용하면 돈 버그 수정이 일부 사이트에 빠진다. 「코드 1벌 + 설정」을 지켜야 한다 | 같다. 템플릿마다 코드 1벌을 규칙으로 둔다 |
| 마이그레이션 누락 | 없다 | 사이트마다 버전이 다를 수 있다. 버전 기록과 일괄 적용 도구가 필요하다 | 같다 |
| 기존 사이트를 옮기는 위험 | tomo·키라팝 데이터를 에어쉽 DB 로 옮긴다. 회원·원장 이전 사고가 난다 | 에어쉽·요루를 둘로 쪼갠다. 회원·바우처 이전 사고가 난다 | 아무것도 옮기지 않는다 |
| 한 화면 관리 | 쉽다 | 운영 API 규격이 있어야 한다 | 같다. 12번 브리지가 그 시작이다 |

### 2.2 추천과 근거

**(다) 혼합을 추천한다.** 외부 고객사를 받을 때 가장 큰 사고는 셋이다. 다른 고객사 데이터가 보이는 것, 고객사 돈이 Ren 계정에 섞이는 것, 한 고객사 장애가 전부를 멈추는 것이다. 분리형은 이 셋을 구조로 막는다. 공유형은 정책과 주의로 막는다. 이미 도는 사이트를 옮기는 것 자체도 사고 원인이므로 에어쉽·요루는 그대로 둔다.

분리형의 약점은 둘이다. 코드가 갈라지는 것과 마이그레이션이 빠지는 것이다. 둘 다 규칙과 도구로 막는다(6장 관문 9·10).

### 2.3 각 사이트를 놓는 자리

| 사이트 | 소유 | DB | 센터 연결 방식 | 센터에서 하는 일 | 비고 |
|---|---|---|---|---|---|
| 에어쉽 | Ren | 에어쉽 DB | 내장(센터가 지금 에어쉽 어드민 안에 있다) | 전부 | 센터를 떼어 낼 때(3단계) 운영 API 기본 등급을 붙인다 |
| 요루 | Ren | 에어쉽 DB(brand 칸) | 내장 | 전부 | 쪼개지 않는다. `x-brand` 헤더 신뢰는 Ren 사이트 사이에서만 허용한다. 외부 고객사를 이 방식으로 넣지 않는다 |
| tomo | Ren | tomo DB | 브리지(12번 설계) | 조작 + 돈 조작(소유자) | 연결 사이트 1호. 규격을 여기서 굳힌다 |
| 키라팝 | 비케이온(다른 법인) | 키라팝 DB | 브리지(같은 규격) | 처음에는 읽기·건수·CS·주문 상태. 돈 조작은 키라팝 어드민에 둔다 | 외부 고객사 1호 시험. 통계·돈을 Ren 사이트와 합치지 않는다 |
| 외부 고객사(구매대행·배대지) | 고객사 | 고객사마다 새 DB·새 배포(에어쉽 코드 1벌) | 브리지 기본 등급 + 자기 배포의 어드민 | 건수·알림·AI 직원. 깊은 조작은 그 배포 어드민에서 한다 | 3단계부터 |

### 2.4 운영 API 등급

| 등급 | 들어 있는 것 | 누가 구현하나 | 센터가 얻는 것 |
|---|---|---|---|
| 기본(필수) | 상태(`health`), 자기소개(`meta`: 규격 버전·기능 선언), 건수(`counts`), 이벤트 알림(훅), 깊은 링크 | 모든 연결 사이트 | 홈 합치기, 시스템 상태, 알림, 사이트 전환 |
| 조작(선택) | 기능별 목록·상세·상태 변경·답변 | 센터에서 직접 조작할 사이트(tomo, 이후 키라팝) | 센터 화면에서 처리 |
| 돈(선택) | 환불 실행·출금 확정·분쟁 환불 | 소유자가 같은 사이트만(tomo) | 센터에서 돈 조작 |

- 에어쉽 코드로 만든 고객사 사이트는 「기본」으로 시작한다. 조작 길이 그 배포의 서버 함수 하나로 남는다. 조작 길이 둘이면 값이 갈라지는 사고가 난다.
- AI 직원이 필요한 조작(문의 답변 게시, 고객 안내 발송)만 「조작」 등급으로 먼저 올린다.

## 3. 12번 설계에 주는 영향

12번은 TOMO 전용 이름으로 쓰였다. 에어쉽 쪽 A1 과 tomo 쪽 T3 가 아직 병합 전이다. 이름을 지금 바꾸면 운영 데이터가 없어 사고가 없다. 나중에 바꾸면 표 이름·권한 키·알림 링크·직원 즐겨찾기가 함께 깨진다.

### 3.1 지금 반영할 최소 변경

| # | 12번 원안 | 바꿀 것 | 왜 지금인가 |
|---|---|---|---|
| 1 | 에어쉽 표 `tomo_events`, `tomo_ops_log` | `connected_site_events`, `connected_site_ops_log`. 둘 다 `site_key` 칸을 둔다. 유일 제약은 `(site_key, event_id)` | 운영 기록이 쌓인 뒤 표 이름을 바꾸면 기록 대조가 끊긴다 |
| 2 | 「어드민 전용 외부 사이트 목록」(형태 미정) | 표 `connected_sites` 1개: `site_key`, 이름, 소유 구분(`own`/`client`), 주소, 규격 버전, `capabilities`, 통화, 상태, 마지막 성공 시각 | 「보는 사이트」·메뉴·홈이 같은 목록 하나를 읽어야 사이트가 화면마다 다르게 보이지 않는다 |
| 3 | 비밀값 `integration_secrets.provider = 'tomo_ops'` | `provider = 'site:<site_key>'` 규칙(`site:tomo`) | 사이트마다 키를 따로 바꾸고 따로 끊는다 |
| 4 | 권한 키 `tomo.ops`·`tomo.money` 를 `admin_menu_access` 에 둔다 | 새 표 `connected_site_access(user_id, site_key, scopes[])`. **행 없음 = 거부.** 소유자만 기본 전체. scope 는 `ops`·`money` 둘 | `admin_menu_access` 는 「행 없음 = 전체 접근」이다. 그 표에 돈 권한을 두면 제한 행이 없는 직원이 TOMO 환불을 누를 수 있다. 12번 결정 2(소유자만)와 어긋난다 |
| 5 | 라우트 `/admin/tomo/…` | `/admin/sites/$site/…`(`/admin/sites/tomo/proxy`). 화면은 `site_key` 를 인자로 받는다 | 알림 링크·활동 기록 링크·직원 즐겨찾기가 이 주소를 쓴다 |
| 6 | 코드 `src/lib/tomo-bridge.server.ts`, `tomo-types.ts`, `components/admin/tomo/**`, `nav-tomo.ts` | `src/lib/connected/bridge.server.ts`(인자 `siteKey`), `src/lib/connected/types.ts`, `src/components/admin/connected/**`, `nav-connected.ts` | 두 번째 사이트를 붙일 때 복사본이 생기면 수정이 한쪽에 빠진다 |
| 7 | 훅 `/api/tomo-hook` | `/api/site-hook/$site`. 토큰은 사이트마다 다르다 | 한 사이트 토큰이 새도 다른 사이트 이벤트를 꾸밀 수 없다 |
| 8 | 메뉴 그룹 「TOMO」 고정 | `connected_sites` 행마다 그룹 하나. 항목은 그 사이트 `capabilities` 에 있는 것만 그린다 | 없는 기능의 빈 화면이 뜨면 직원이 「0건」으로 읽는다 |
| 9 | 배지 키 `tomo` | `site:<site_key>` 형식(`site:tomo`) | 사이트가 늘 때 배지 정의를 다시 고치지 않는다 |
| 10 | tomo API: 규격 버전 없음 | `GET /api/ops/meta` 추가. 요청 헤더 `x-ops-version: 1`. 모든 응답에 `api_version` | 버전 없이 시작하면 나중에 뜻이 바뀐 칸을 구별할 수 없다 |
| 11 | tomo API 권한 값 `tomo.ops`·`tomo.money` | 규격에서는 `scope: "ops" \| "money"` | 사이트 이름이 규격에 박히면 다른 사이트가 못 쓴다 |
| 12 | 응답 칸 `center_airship`(KR/JP) | `center_country`(ISO 두 글자) | 규격에 에어쉽 이름이 남지 않게 한다 |
| 13 | tomo 칸·변수의 「에어쉽」 이름: `ops_actors` 의 에어쉽 관리자 id, `AIRSHIP_HOOK_TOKEN` | `center_actor_id`·`center_actor_email`, `OPS_HOOK_URL`·`OPS_HOOK_TOKEN` | 센터를 떼어 내면 부르는 쪽이 에어쉽이 아니다 |
| 14 | 이벤트 종류가 한글 설명뿐 | 종류 이름을 규격으로 고정한다(3.3) | 센터 알림·AI 직원이 종류 이름으로 규칙을 건다 |
| 15 | `counts` 응답 형태 미정 | 배열 `[{ key, label, count, overdue, capability, url }]` | 센터가 사이트별 키를 몰라도 홈에 그린다 |

- 범위 제한: 이 15가지는 이름·표·칸·주소만 바꾼다. 12번의 흐름·돈 경로·멱등 규칙·완료 기준은 그대로다.
- 부작용 확인: `connected_sites` 는 `public.sites` 와 다른 표다. `public.sites` 는 도메인 판정·사이트맵·메일 발신에 쓰인다. 12번 3.6 의 「`sites` 에 행을 넣지 않는다」는 그대로 지킨다.

### 4.1 고객사가 설정으로 바꾸는 것과 하드코딩 제거 순서

| 순위 | 설정 항목 | 지금 | 바꿀 방향 | 값이 틀리면 생기는 일 |
|---|---|---|---|---|
| 1 | 결제 계정(Stripe 키·웹훅 비밀) | 키 1세트 | 배포마다 자기 키. 값이 없으면 결제 화면을 닫는다 | 고객사 매출이 다른 계정으로 들어간다 |
| 1 | 입금 계좌·예금주 | TS 상수 / DB 1행 | `site_settings` | 고객이 남의 계좌로 입금한다 |
| 1 | 사업자 정보 표기(상호·대표·주소·연락처) | TS 상수 | `site_settings` | 고객 화면에 다른 회사가 나온다 |
| 1 | 알림 발신(메일 주소, 알림톡 프로필, 운영자 텔레그램) | 전역 | 배포마다. 값이 없는 채널은 끈다 | 다른 이름으로 고객 알림이 간다 |
| 2 | 수수료표 | TS 상수 | DB 표 + 적용 시작 시각. 주문에 적용 값을 찍어 둔다 | 청구액이 틀린다 |
| 2 | 환율 가산 값 | TS 상수 | `site_settings`(서버만 읽는다. 고객 화면에 숫자를 내지 않는다) | 마진이 틀린다 |
| 2 | 통화·청구 통화 | 센터별 규칙이 코드에 있다 | 템플릿 기본값 + 설정 | 청구 통화가 틀린다 |
| 3 | 센터 주소·수취인 표기 | 코드·DB 혼재(확인 못 함) | `site_settings` | 짐이 다른 창고로 간다 |
| 3 | 도메인·사이트 이름·로고·색 | `public.sites` + 상수 | 배포 설정 | 화면 혼란 |
| 3 | 약관·이용안내·요금 안내 글 | 코드 | 설정에서 고르는 기본 글 + 고객사 수정 | 안내와 실제 요금이 다르다 |
| 4 | 워커 계정(마켓 로그인), 택배·통관 연동 키 | 전역 | 배포마다 | 6장 관문 7 |

- 방식: `site_settings` 는 서버에서만 읽는다. 분리형이라 DB 마다 한 행이면 된다.
- 시작 검사: 1순위 값이 하나라도 비면 그 배포는 결제·입금 안내·알림 발송을 닫고 어드민에 「설정 미완료」를 띄운다. 기본값으로 Ren 사이트 값을 쓰지 않는다. 이것이 가장 큰 사고(남의 계좌·남의 이름)를 막는다.
- 브랜드 판정: 외부 고객사 배포에서는 `x-brand` 헤더를 읽지 않는다. 배포 하나가 사이트 하나다.

### 5.2 승인 규칙(제품 기본값)

| 일의 종류 | 최고 수준 | 수준 3 조건 |
|---|---|---|

| 상태 변화 안내(지연·품절·통관 보류·통관번호 불일치) | 3 | 상태가 데이터로 확인됐다. 같은 건에 같은 안내를 보낸 적이 없다 |

- 공통 규칙 1: 근거를 읽지 못하면(사이트 응답 없음) 추측으로 채우지 않고 멈춘다.
- 공통 규칙 2: 실행 전에 중복 검사를 한다. 같은 대상·같은 동작의 기록이 원장에 있으면 실행하지 않는다.
- 공통 규칙 3: 고객사는 수준을 낮출 수 있다. 올리는 것은 위 표의 최고 수준까지만 된다.

## 6. 고객사를 받기 전 필수 관문

| # | 관문 | 최소 해법 | 통과 증거 |
|---|---|---|---|
| 1 | 데이터 격리 | 고객사마다 DB·배포를 따로 둔다. 센터에는 주문·회원 정본을 두지 않는다. 이벤트 본문에 개인정보를 넣지 않는다 | 고객사 A 의 키로 고객사 B 주소를 불러 401 이 난다. 센터 DB 에 주소·통관번호 칸이 없다 |
| 2 | 고객사 직원 권한 | 고객사 직원은 자기 배포 어드민에만 로그인한다. 센터 권한은 `connected_site_access`(행 없음 = 거부) | 권한 없는 계정으로 사이트 목록·건수·조작이 모두 거부된다 |
| 3 | 고객사 결제 계정 | 고객사 본인의 결제 계정·계좌를 그 배포에만 넣는다. Ren 계정을 거치지 않는다 | 시험 결제 1건이 고객사 계정에만 남는다. Ren 계정 웹훅에 그 이벤트가 오지 않는다 |
| 4 | 도메인 연결 | 배포마다 도메인 하나. 연결 뒤 메일 발신 도메인 인증까지 확인한다 | 고객사 도메인에서 가입 메일이 고객사 이름으로 온다 |
| 5 | 요금 청구 | 처음 3곳은 수동 청구 + 센터에 납부 상태 칸. 미납 시 차단 순서를 문서로 둔다(안내 → AI 정지 → 어드민 읽기 전용. 고객 화면과 진행 중 주문은 끊지 않는다) | 미납 시험 계정에서 순서대로 동작한다 |
| 6 | 내보내기·삭제 | 「전체 내보내기」 버튼(주문·회원·돈 기록 CSV + DB 덤프 요청). 해지 시 배포·DB 를 통째로 지운다 | 내보낸 파일의 건수가 DB 건수와 같다 |
| 7 | 워커 공유 | 마켓 로그인 워커(경매·타오바오 등)는 고객사끼리 공유하지 않는다. 고객사 계정으로 따로 띄우거나 그 기능을 끈다 | 고객사 사이트의 입찰이 Ren 야후 계정으로 나가지 않는다 |
| 8 | 장애 격리 | 센터 → 사이트 호출에 타임아웃을 건다. 실패는 「확인 못 함」이다. 사이트는 센터 없이도 판다 | 사이트 하나를 끈 채로 센터 홈과 다른 사이트가 정상이다. 센터를 끈 채로 사이트 주문이 된다 |
| 9 | 코드 1벌 | 고객사별 포크를 금지한다. 차이는 설정과 기능 스위치로만 둔다 | 고객사 배포 전부가 같은 커밋이다 |
| 10 | 마이그레이션 일괄 적용 | 사이트별 스키마 버전을 센터 시스템 상태에 보여 준다. 적용은 한 곳 → 확인 → 나머지 순서로 한다 | 버전이 다른 사이트가 있으면 경고가 뜬다 |
| 11 | 사이트 혼동 방지 | 센터 조작 화면에 사이트 이름 띠를 고정한다. 돈 조작 확인 창에 사이트 이름을 적는다 | 화면 검수 |
| 12 | 고객사 CS 창구 | 고객사가 Ren 에게 묻는 길 하나(센터 안 문의)와 응답 기준을 정한다 | 문의 1건 왕복 |

## 7. 단계별 로드맵

| 단계 | 목표 | 하는 일 | 완료 기준 | 다음 단계로 넘어가도 되는 증거 |
|---|---|---|---|---|
| 0 (지금) | tomo 위험 수정 + 브리지 | 12번 T1~T4, A1~A3. 3.1 의 15가지 이름 변경을 넣는다 | 12번 각 트랙 완료 기준. `/api/ops/meta` 가 버전 1 과 기능 목록을 돌려준다 | 시험 환불 1건이 tomo `refunds` 와 Stripe 에 한 번만 남는다. tomo 를 끈 상태에서 에어쉽 홈이 「확인 못 함」을 보여 준다 |
| 1 | 내 사이트 3개를 한 화면에서 | 「보는 사이트」가 `connected_sites` 를 읽는다. 홈 「내 차례」 합치기. `connected_site_access`. 사이트 이름 띠 | Ren 이 tomo 어드민에 들어가지 않고 하루 운영을 끝낸다(콘텐츠 화면 제외) | 4주 동안 사이트를 헷갈린 답변·환불이 0건이다. 브리지 조작의 「결과 확인 못 함」이 모두 원인까지 판정됐다. 두 기록(tomo `ops_requests`, 에어쉽 `connected_site_ops_log`)이 요청 id 로 전부 맞는다 |
| 2 | 키라팝을 외부 고객사 1호로 연결 | 키라팝에 운영 API 기본 등급 → 조작 등급(문의·주문 상태). 돈 조작은 연결하지 않는다. 규격에 없던 것을 버전 1 에 칸 추가로 넣는다 | 센터에서 키라팝 건수·문의·주문 상태를 다룬다. 통계·돈이 Ren 사이트와 합쳐 보이지 않는다 | tomo 용 화면 코드를 복사하지 않고 키라팝이 붙었다(같은 화면 + 기능 선언). 규격을 깨는 변경이 0건이었다. 4주 무사고 |
| 3 | 템플릿·개설·요금 | 에어쉽 하드코딩 제거(4.1 순위 1 → 3). `site_settings` + 시작 검사. 센터를 따로 배포한다. 개설 절차서(새 DB·배포·도메인·결제 계정·알림). 관문 1~12 | 시험 고객사 배포 1개를 절차서만 보고 만든다. 관문 12개 통과 증거가 모두 있다 | 시험 배포에서 결제 → 구매 → 입고 → 발송 → 환불 한 바퀴가 돈다. 그동안 Ren 계정·계좌·발신 이름이 한 번도 나오지 않는다. 외부 고객사 1곳이 유료로 4주 쓴다 |
| 4 | AI 운영 직원 제품화·모집 | 5.4 의 3가지. `ai_rules`·`ai_actions`. 사용량 집계. 모집 페이지 | 고객사가 규칙을 직접 켜고 끈다. 원장에 모든 자동 처리의 근거가 남는다 | 자동 답변의 사후 정정 비율이 Ren 이 정한 기준 아래다. 돈·외부 제출의 자동 실행이 0건이다(수준 2 까지). 고객사 3곳의 월 AI 원가가 포함량 요금 안에 든다 |

- 개설 자동화(버튼 한 번에 사이트 생성)는 3단계 완료 기준이 아니다. 절차서로 3곳을 연 뒤에 자동화한다. 손으로 해 보지 않은 절차를 자동화하면 빠진 설정이 그대로 복제된다.
- 순서를 바꾸지 않는다. 2단계(키라팝) 없이 3단계로 가면 규격이 tomo 하나에만 맞춰진 채 고객사를 받게 된다.

## 8. 요금 모델 초안

**아래 숫자는 모두 초안이다. 원가(고객사당 DB·배포·AI 호출 비용)를 3단계 시험 배포에서 실제로 잰 뒤 고친다.**

| 상품 | 대상 | 초기비(초안) | 월(초안) | AI 포함량(초안) |
|---|---|---|---|---|
| 연결형 | 이미 사이트가 있는 운영자. 센터 + AI 직원만 쓴다 | 연결 작업 50만원 | 9.9만원 | 월 300대화 |
| 개설형(구매대행·배대지) | 사이트를 새로 만드는 고객사 | 300만원 | 39만원 | 월 500대화 |
| 개설형 + 운영 설계 | 위 + Ren 이 요금표·안내문·규칙을 같이 잡아 준다 | 500만원 | 39만원 | 월 500대화 |
| AI 추가 | 포함량 초과 | — | 500대화마다 10만원(대화당 200원꼴) | — |

| 비교 | 초기비 | 월 | AI |
|---|---|---|---|
| 더그리드 | 500~700만원 | 25~40만원 | — |
| 글로싱 | 350만원 | 20~45만원 | — |
| 네오티소프트 | 110만원 | 20만원~ | — |
| 카페24 / 아임웹(일반 몰) | 무료 / — | 무료 / 2.2~3.3만원 | 카페24 AI 월 7천원 |
| 채널톡 | — | — | 대화당 500~700원 |
| **이 제품(초안)** | 임대 솔루션의 중간 아래 | 임대 솔루션의 위쪽 | 포함량 + 구간 정액 |

- 위치: 초기비는 낮추고 월 요금에 AI 직원을 넣는다. 「사이트 임대」가 아니라 「사이트 + 운영 직원」으로 판다.
- 구간 정액으로 두는 이유: 1인 운영자는 달마다 청구액이 달라지는 것을 싫어한다. 대화당 과금은 문의가 몰린 달(배송 지연 사고)에 요금이 뛰어 불만이 생긴다.
- 약속 2가지를 요금표에 같이 적는다: 데이터 전체 내보내기, 해지 뒤 일정 기간 읽기 전용 접속. 「솔루션 업체 폐업」 불안을 줄이는 자리다.
- 일반 쇼핑몰 단독 상품은 요금표에 넣지 않는다.
